# V1.0 Governance Contract

## 1. Scope and invariants

This contract defines the V1.0 production-governance mock boundary. It adds a traceable diagnosis-to-review loop over the existing read-only V0.8/V0.9 data contracts. All metrics are synthetic Mock/Replay values; this version uses no real media credentials, no real media write API, and does not claim production readiness or verified business gains.

The following invariants are mandatory:

- Every diagnosis conclusion references a rule, the metric inputs used, and valid `EV-*` evidence.
- Missing, stale (数据过期，即 P5 的 `stale`), or conflicting data produces a safe degradation/refusal, never a deterministic guessed conclusion.
- Agent output is limited to diagnosis and a structured draft. It never changes budget, bid, strategy, experiment, or media configuration.
- Permission and tenant-boundary failures are rejected identically in UI and server/domain logic and are audited.
- Existing V0.8 scope `current_rta_only` remains the minimum read scope.

## 2. Tenant and request context

Every command and query carries a server-injected context:

```js
{
  tenantId: 'tenant-a',
  operator: 'user-optimizer-01',
  role: 'optimizer',
  scope: 'current_rta_only',
  requestId: 'req-...'
}
```

`tenantId` is authoritative from the authenticated session; a browser-supplied tenant is ignored. All `taskId`, `rtaId`, evidence, drafts, and audit events must belong to that tenant. A cross-tenant lookup or mutation returns `CROSS_TENANT_DENIED`, performs no state change, and emits an audit event with `action: cross_tenant_access` and `result: denied`. V1.0 includes at least two Mock tenants (`tenant-a`, `tenant-b`) to exercise this boundary.

## 3. Roles and minimum permissions

The only Mock roles are `observer`, `optimizer`, and `approver`. `close` is intentionally not an action available to `observer`; closure is a state transition governed by the owner/approver workflow.

| Action | observer | optimizer | approver |
| --- | --- | --- | --- |
| `view_task` | ALLOW | ALLOW | ALLOW |
| `view_diagnosis` | ALLOW | ALLOW | ALLOW |
| `view_evidence` | ALLOW | ALLOW | ALLOW |
| `confirm_diagnosis` | DENY | ALLOW | DENY |
| `create_draft` | DENY | ALLOW | DENY |
| `edit_draft` | DENY | ALLOW | DENY |
| `submit_draft` | DENY | ALLOW | DENY |
| `approve` | DENY | DENY | ALLOW |
| `reject` | DENY | DENY | ALLOW |
| `record_execution` | DENY | ALLOW | DENY |
| `view_audit` | ALLOW | ALLOW | ALLOW |
| `view_review` | ALLOW | ALLOW | ALLOW |
| `approve_draft_execution` | DENY | DENY | ALLOW |

`confirm_diagnosis` includes confirm and reject diagnosis decisions; `reject` is reserved for rejecting an approval-stage draft. `approve_draft_execution` only authorizes a simulated/manual execution record and never invokes a media write interface. An unauthorized action is denied in both UI and service/domain layers and creates an audit event with `result: denied`; no partial mutation is permitted.

## 4. Diagnosis and evidence hand-off

Diagnosis output must carry `{ ruleIds, metricRefs, evidenceIds }`. Each `evidenceIds` member matches the existing legal evidence format `EV-*`, belongs to the same task and tenant, and has source/freshness metadata. Evidence conflict, absent required evidence, or a non-legal identifier blocks confirmation and draft submission with a structured degradation state.

## 5. ActionDraft

The canonical draft shape is:

```js
{
  id, taskId, title,
  target: { rtaId, media, project, experiment },
  suggestedActions: [/* adjust bid | pause | scale, demonstration only */],
  diff: { before: {}, after: {}, demonstrative: true },
  successMetrics: [{ name, target, observationWindow }],
  stopRollbackConditions: [{ condition, action }],
  risks: [{ description, severity }],
  evidenceIds: ['EV-...'],
  ownerRole: 'optimizer',
  createdAt, updatedAt, version,
  status: 'draft'
}
```

`diff` is explanatory only. It is not an executable patch. `version` increments on every edit; stale version writes are rejected. `ownerRole` is `optimizer` for V1.0 drafts. A draft can be submitted only when required fields, legal evidence, tenant scope, and diagnosis confirmation are present.

### 5.1 Formal state machine

| State | Allowed role(s) | Allowed transition and condition |
| --- | --- | --- |
| `draft` | optimizer | `edit_draft` remains here; `submit_draft` -> `pending_approval` after validation |
| `pending_approval` | approver | `approve` -> `approved`; `reject` -> `rejected` with reason |
| `approved` | approver | `approve_draft_execution` -> `execution_recorded` for simulated/manual record only |
| `rejected` | optimizer | `edit_draft` creates a new version -> `draft`; no execution allowed |
| `execution_recorded` | optimizer | `record_execution` records operator/time/details -> `observing` |
| `observing` | optimizer | observation window and evidence complete -> `reviewed`; explicit no-data/aborted outcome -> `closed` with reason |
| `reviewed` | optimizer or approver | `reviewed` -> `closed` after review is recorded |
| `closed` | none | terminal; only read and audit queries |

No transition from `draft`, `pending_approval`, or `rejected` can record execution. `record_execution` records a human action or a clearly labelled simulation; it never calls a budget, bid, strategy, experiment, or media write API.

### 5.2 Mapping from existing `STATES`

The mapping is a compatibility translation, not a second state machine.

| Existing `STATES` key in `demo/V1.0/index.html` | V1.0 meaning | V1.0 state/event |
| --- | --- | --- |
| `idle` | no active task | no `ActionDraft`; task not started |
| `reading` | provider read in progress | pre-draft; audit `initiate_diagnosis` |
| `diagnosing` | rule evaluation in progress | pre-draft; audit `initiate_diagnosis` |
| `completed` | diagnosis produced | diagnosis ready; `confirm_diagnosis` may be next |
| `pending` | awaiting human confirmation/approval | diagnosis confirmation or approval is pending; no execution |
| `insufficient` | insufficient evidence/data | degradation `partial` or `stale`; no conclusion/draft transition |
| `executing` | approved, waiting for human action | `approved` (or compatibility display before `record_execution`) |
| `waiting` | waiting for return data | `observing`; audit observation start |
| `reviewed` | review visible | `reviewed`; may close after review record |
| `failed` | legacy generic failure/rejection display | `rejected` when approval was rejected, otherwise terminal task error; never executable |

The mapping is a compatibility translation, not a second state machine. The following are UI-triggered action functions, not `STATES` members:

| UI action function | V1.0 action / state transition | Authority note |
| --- | --- | --- |
| `approvePlan` | compatibility display/action; maps to `approve` -> `approved` only when executed by `approver` | display does not confer approval authority |
| `modifyPlan` | `edit_draft` while `draft`; increment `version` | display does not confer approval authority |
| `rejectPlan` | `reject` -> `rejected` with reason | formal approval workflow remains server/domain-controlled |
| `markExecuted` | `record_execution`: `approved` -> `execution_recorded` -> `observing` | human/simulated execution record only |
| `markReviewed` | `review`: `observing` -> `reviewed` | records review; does not execute a plan |

`approvePlan`/`modifyPlan` display does not represent approval authority in V1.0: formal approval is only `approve` by `approver` and produces `approved`.

## 6. Audit timeline

The canonical business sequence is: `discover_anomaly` -> `initiate_diagnosis` -> `view_evidence` -> `confirm_diagnosis` -> `create_draft` -> `submit_draft` -> `approve`/`reject` -> `record_execution` -> `observe` -> `review`.

Every event conforms to:

```js
{
  taskId, action, operator, role, timestamp,
  beforeStatus, afterStatus, evidenceIds, result
}
```

`result` is at least `allowed`, `denied`, `rejected`, `degraded`, or `success`. Queries support `GET /audit?taskId=...`, plus `operator` and/or `role` filters. The returned order is timestamp ascending with a stable event id/sequence in the implementation.

Mock audit proves linkage and traceability only. It does not claim regulatory immutability or compliance certification. A production design may append hash-chain links, sign events with a managed key, use append-only storage, and periodically anchor a digest externally; credentials and signing keys remain server-side and outside client, Git, Mock, and logs.

## 7. Degradation and stability display

| State | Trigger | Affected capability | Display copy | Next suggestion |
| --- | --- | --- | --- | --- |
| `normal` | required data fresh and consistent | diagnosis and permitted workflow | `数据完整，可继续诊断` | view evidence and continue |
| `stale` | freshness threshold exceeded | diagnosis confirmation and draft submission | `数据已过期，暂不形成确定结论` | refresh/replay a newer sample |
| `partial` | required fields/evidence missing | affected diagnosis branch and draft creation | `数据部分缺失，无法完成可靠判断` |补齐字段或缩小范围 |
| `timeout` | upstream/replay request timed out | current read and downstream diagnosis | `上游超时，已安全降级` | retry with bounded policy or inspect cached data |
| `permission_denied` | role lacks action or resource permission | requested action only | `当前角色无权执行此操作` | request authorized review/approval |
| `cross_tenant_denied` | resource tenant differs from context tenant | requested resource/action | `跨租户访问已拒绝` | switch to an authorized tenant context |

Conflicting evidence is represented as `partial` with a conflict detail and blocks deterministic diagnosis. `stale`, `partial`, and `timeout` cannot be silently rendered as `normal`.

## 8. Design-and-test boundaries for production concerns

- Tenant isolation: inject `tenantId`, enforce it at query and command boundaries, and test `tenant-a` versus `tenant-b` cross-access denial.
- Token rotation and key custody: define server-only environment names such as `MEDIA_TOKEN_REF` and `AUDIT_SIGNING_KEY_REF`; never place token values in browser state, fixtures, Git, or audit events. Rotation is an interface/test scenario, not a real credential integration.
- Rate limiting, circuit breaking, retry, and alerting: model bounded states (`rate_limited`, `open`, `half_open`, `retry_exhausted`) and offline assertions; do not connect a monitoring platform.
- Audit tamper resistance: use the production hash/signature/append-only design above; Mock only checks event shape, order, linkage, and denied-action traceability.

## 9. Contract version and compatibility

This document is `v1.0`. It extends, and does not replace, V0.8 read-only provider behavior and V0.9 field mapping. Any implementation that adds a real media write, accepts a client tenant as authority, bypasses approval, or converts synthetic outcomes into business-effect claims violates this contract.
